# Concepts

Five ideas, in the order a build uses them.

## 1. The base skill

A base skill is a directory holding a `SKILL.md` and optional bundled files, in the open Agent
Skills format. It is plain markdown with YAML frontmatter, valid and directly usable by any
harness that reads skills, with or without skillforge.

skillforge-specific configuration lives under `metadata.skillforge` in the frontmatter, which
the Agent Skills format reserves for arbitrary data. The build strips it, so rendered output
carries only provenance.

Written by: whoever owns the library. Reference: [authoring-skills.md](authoring-skills.md).

## 2. Params

Params are **values**, never structure. A base declares each param's type, description and
default; a consumer supplies values; the body reads them as `{{ params.name }}`.

Values layer: the base's `default` < the consumer's repo-wide `params:` < that skill's own
`params:`. A repo-wide param a skill does not declare is ignored, because it exists for
whichever skills do declare it. A per-skill param the skill does not declare is an error,
because that is always a typo.

## 3. Anchors

Anchors are **structure**. They are HTML comments, so they are invisible in rendered markdown
and harmless to a harness that never heard of skillforge.

- A **block** is a named, replaceable region. It can carry a `when` expression, and disappears
  from the output when that expression is false.
- A **point** is a named insertion site with no content of its own.

Anchors are a base author's deliberate contract: *these* are the passages a consumer may
change. Everything else is the skill's substance.

## 4. Patches

A patch is one operation a consumer applies to one target. Targets come in two flavours:

- **Anchors** (`block:`, `point:`) — the stable contract. Renaming one is a breaking change to
  the skill, the same as renaming a function.
- **Heading paths** (`heading:`) — the escape hatch, for patching a skill whose author never
  anticipated your need, including skills in repositories you do not control. Heading paths are
  unstable by nature, so every heading patch must pin the target section's content hash. When
  upstream edits that section, the build fails and names the new hash instead of silently
  patching the wrong thing.

If neither is enough, `skillforge eject` copies the skill into your repo and cuts the link.
That is a deliberate, visible exit, not a slow drift.

## 5. Layers

A `skillforge.yaml` can `extends` another one, from a git source or a path. Layers apply in
declared order: an org layer, then a team layer, then the project. Params and skill lists merge;
patches accumulate.

When two layers patch the same target, the build fails. The later layer takes the target by
declaring `force: true`, which leaves a record in the config that the override was deliberate.
Forcing **replaces** the earlier layer's patches on that target rather than stacking on them, so
anything from the earlier patch that should survive has to be restated. Two patches in the
*same* layer both apply, in order, because that is one author's intent.

## Output and targets

The build renders every configured skill into `output:` (default `.agents/skills/`). That
directory is the canonical artifact and is committed.

Adapters then translate it into whatever each harness reads. Adapters are the only part of
skillforge that knows a harness exists. See [adapters.md](adapters.md).

Every generated byte is recorded in `skillforge.lock`, so `skillforge check` can prove the
committed output still matches the configuration that produced it.
